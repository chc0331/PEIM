# 통합·회귀·몽키 테스트와 계획서

## 서브노트

### 한눈에 이해

통합은 연결부의 계약을, 회귀는 변경이 기존 동작을 깨뜨리지 않았는지를, 몽키는 무작위 조작에서의 견고함을 살핍니다.

### 정의와 핵심 원리

통합 테스트는 결합된 컴포넌트·시스템의 인터페이스와 상호작용을 확인하는 시험입니다. 통합 전략은 결함 위치 파악·실행 가능한 부분 시스템·임시 대역 비용을 함께 고려해 선택합니다.

- 비점진적 Big Bang은 모든 구성요소를 한꺼번에 연결하므로 준비는 단순할 수 있으나 결함 원인 분리가 어렵고 시험 시작이 늦어집니다. 점진적 통합은 작은 묶음씩 연결해 결함 위치를 좁히고 조기 피드백을 얻습니다.
- 하향식은 상위 제어에서 하위로 내려가며 아직 없는 하위 모듈을 Stub으로 대체합니다. 상향식은 하위 기능부터 상위로 결합하고 상위 호출자를 Driver로 대체합니다. 혼합 통합은 계층 특성과 위험에 따라 두 방향을 조합합니다.
- 회귀 테스트는 수정·환경변경 뒤 영향받는 기존 기능이 유지되는지 확인합니다. 확인 테스트는 특정 결함이 실제 수정됐는지 재시험하는 것으로 회귀와 목적이 다릅니다. 몽키는 무작위 또는 의사무작위 이벤트로 충돌·예외·자원 문제를 찾고 seed·이벤트 수를 보관하면 재현성을 높일 수 있습니다.
- 통합 시험계획서는 목적·범위·제외, 대상/버전·연계 목록, 전략·일정·역할, 환경·도구·대역·데이터, 테스트 기법·케이스/추적, 진입·종료 기준, 결함 처리·재시험/회귀, 위험·대응, 산출물·승인을 담아야 합니다.

### 구조·비교·판단

| 구분 | 원리·특징 | 적용·판단 |
| --- | --- | --- |
| 하향식 | 상위 흐름 우선, Stub 필요 | 조기 업무 흐름 확인 |
| 상향식 | 하위 기능 우선, Driver 필요 | 기초 모듈 안정화 |
| 회귀/몽키 | 기존 행동 보호 / 무작위 견고성 탐색 | 체계적 요구 커버리지를 서로 대체하지 않음 |

### 적용 예제

**강사 창작 적용 예시: 주문-결제 통합**

강사 생성 학습 예제입니다. 공식 기준답안이 아닙니다.

**조건:** 주문 모듈은 있고 외부 결제 샌드박스는 다음 주 준비됩니다.

1. 결제 Stub으로 승인·거절·지연 응답을 정해 주문 흐름부터 시험합니다.
2. 샌드박스가 준비되면 실제 계약·타임아웃·중복 요청을 통합합니다.
3. 결제 수정 후 주문·취소 회귀시험, 무작위 UI 이벤트는 seed와 함께 별도로 수행합니다.

**결과·해석:** 부품 대역에서 실제 연계로 가며 위험을 단계적으로 확인합니다.

**전제·주의:** Stub만 통과했다고 외부 결제 연계가 검증됐다고 표시하지 않습니다.

### 답안 골격과 혼동 방지

통합 목적·점진/비점진 비교 → Top-down/Bottom-up·Stub/Driver → 몽키/회귀·계획서 항목

- Stub과 Driver의 호출 방향을 바꾸지 않습니다.
- 몽키가 통과해도 업무 규칙이 맞다는 증거는 부족합니다.

### 내용을 가리고 회상

1. 하향식 통합에서 없는 하위 모듈은 무엇으로 대체합니까?
2. 확인 테스트와 회귀 테스트는 어떻게 다릅니까?
3. 무작위 시험을 재현하려면 무엇을 남겨야 합니까?

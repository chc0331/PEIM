# 코드형 인프라 IaC

## 서브노트

### 한눈에 이해

인프라 구성을 코드로 적어 두면 누가 어떤 값을 바꾸려는지 검토하고, 검토한 구성을 다시 만들 수 있습니다.

### 정의와 핵심 원리

코드형 인프라(IaC)는 기계가 읽을 수 있는 정의로 인프라 자원을 관리합니다. 코드를 버전별로 보관하고 검토하면 배포를 자동화하고 구성을 재현할 수 있습니다. 선언형은 원하는 상태를, 명령형은 수행 절차를 적습니다.

- 구성을 정의하고 검증한 뒤 변경 계획을 검토해 적용합니다. 적용 결과도 관찰합니다. Terraform의 plan은 변경 계획을 만들고 apply는 변경을 실행합니다. 생성뿐 아니라 삭제·대체, 의존 자원의 변경 순서와 서비스 중단 가능성도 살핍니다.
- 상태 파일은 코드로 관리하는 자원과 실제 자원을 연결합니다. 잠금과 접근 통제, 암호화, 버전 보호가 필요합니다. 비밀값이 코드나 상태에 남을 수 있으므로 별도 비밀 관리 체계를 사용합니다. 수동 변경으로 실제 구성과 정의가 달라지는 현상(drift)은 정기적으로 변경 계획을 확인하고 정책을 검사해 찾습니다.
- 검증된 모듈과 템플릿은 반복 작업을 줄입니다. 지나치게 추상화하면 무엇이 바뀌는지 보기 어려워집니다. 자동 배포 과정에는 정책 검사, 승인, 최소 권한, 공급망 서명 검증, 복구 절차를 연결합니다. 일부 변경이 실패할 수 있으므로 복구 방법도 미리 정합니다.

### 구조·비교·판단

| 구분 | 핵심 원리 | 적용·한계 |
| --- | --- | --- |
| 수동 관리 | 콘솔과 문서에 따라 변경 | 변경 누락, 재현 어려움 |
| 선언형 IaC | 원하는 상태와 실제 상태의 차이 계산 | 상태와 제공자 플러그인 관리 |
| 명령형 자동화 | 수행할 작업의 순서 명시 | 중간 실패와 반복 실행의 안전성 |

### 적용 예제

**운영 DB의 의도치 않은 대체 방지**

강사 생성 학습 예제입니다. 공식 기준답안이 아닙니다.

**조건:** 스토리지 설정만 바꿀 예정인데 변경 계획에 운영 DB를 대체한다고 표시됩니다.

1. 계획에서 삭제되거나 대체될 자원과 그 자원에 의존하는 서비스의 영향을 확인합니다.
2. 백업에서 복구할 수 있는지, 변경에 쓸 수 있는 시간이 얼마나 되는지 검토합니다.
3. 정책 검사로 승인받지 않은 중요 자원의 삭제를 막습니다.
4. 테스트 환경에서 먼저 검증하고, 검토한 계획을 적용한 뒤 상태를 확인합니다.

**결과·해석:** 코드 한 줄이 바뀌어도 자원이 대체될 수 있습니다. 계획을 적용 전에 검토해 중단 가능성을 줄입니다.

**전제·주의:** 제공자 플러그인이나 API의 버전이 달라지거나 누군가 수동으로 자원을 바꾸면 적용 결과도 달라질 수 있습니다.

### 답안 골격과 혼동 방지

정의와 필요성 → 작성·계획·적용 → 상태 파일과 구성 불일치 → 검토와 보안 → 변경 사례

- 코드로 구성을 관리해도 복구 절차는 따로 연습해야 합니다.
- 상태 파일에 민감 정보가 남을 수 있으므로 접근을 통제합니다.

### 내용을 가리고 회상

1. 변경 계획을 검토하는 단계와 적용하는 단계를 나누는 이유는 무엇입니까?
2. 관리 코드와 실제 자원의 구성이 어떻게 달라질 수 있습니까?
3. 상태 파일 잠금은 무엇을 보호합니까?

# RTO·RPO와 Active-Active·Passive·Pilot Light

## 서브노트

### 한눈에 이해

언제까지 서비스를 다시 열지와 어느 시점의 데이터까지 잃어도 되는지는 서로 다른 목표입니다.

### 정의와 핵심 원리

RTO는 중단 후 허용하는 복구 시간 목표이고 RPO는 복구해야 할 데이터 시점의 목표로 통상 허용 손실 시간 폭으로 표현합니다. BIA로 업무 영향·의존성·우선순위를 정한 뒤 데이터 복제와 실행 환경 준비 수준을 선택합니다.

- Active-Active에서는 여러 사이트가 평소에도 요청을 처리합니다. 장애 시 트래픽을 우회할 경로와 남은 사이트의 용량, 데이터 충돌·일관성, 공통 의존 자원을 확인합니다. 여러 리전을 사용해도 복구 시간과 데이터 손실 폭이 0인지는 별도로 검증합니다. 잘못된 데이터도 복제될 수 있으므로 이전 시점의 백업이 필요합니다.
- Active-Passive에서는 주 사이트가 요청을 처리하고 대기 사이트는 전환 뒤 처리합니다. 대기 사이트를 미리 얼마나 준비했는지에 따라 기동·확장·복원 시간이 달라집니다. Pilot Light는 데이터와 핵심 기반을 준비하고 장애 시 응용 등 추가 자원을 기동합니다. Warm Standby는 이미 가동 중인 작은 규모의 환경을 장애 시 확장합니다.
- 실제 복구에는 장애 탐지와 선언, 복구 결정, DB 승격, 자원 확장, DNS·경로 전환, 인증과 검증 시간이 들어갑니다. 복제 지연을 관찰하고, 백업 복원과 장애 훈련, 주 사이트 복귀(failback), 데이터 일관성을 시험합니다. 목표와 실제 측정값은 구분합니다.

### 구조·비교·판단

| 구분 | 핵심 원리 | 적용·한계 |
| --- | --- | --- |
| Active-Active | 모든 지역 평시 처리 | 비용·쓰기 충돌·잔여 용량 |
| Active-Passive | 대기 지역 전환 후 처리 | 대기 준비 수준별 시간 차 |
| Pilot Light | 핵심 데이터·기반만 가동 | 응용 기동·확장 선행 필요 |
| Warm Standby | 작은 규모 전체 가동 | 즉시 제한 처리 후 확장 |

### 적용 예제

**복구 목표 검증**

강사 생성 학습 예제입니다. 공식 기준답안이 아닙니다.

**조건:** 10:00에 장애가 났고 10:25에 서비스가 복구됐습니다. 복구한 데이터의 마지막 시점은 09:57입니다. 목표는 RTO 30분, RPO 5분입니다.

1. 실제 복구 시간은 25분입니다.
2. 데이터가 마지막으로 복구된 09:57부터 장애가 발생한 10:00까지의 차이는 3분입니다.
3. 25분은 RTO 30분 이내이고, 3분은 RPO 5분 이내입니다. 이번 훈련에서는 두 목표를 모두 충족합니다.
4. 다만 오염 사고·자격 증명 침해·전체 리전 손실 등 다른 시나리오도 시험합니다.

**결과·해석:** 시간 목표와 데이터 시점을 독립적으로 평가합니다.

**전제·주의:** 명시 시각은 가상 훈련 예이며 제품 보장 값이 아닙니다. 복제는 백업의 대체물이 아닙니다.

### 답안 골격과 혼동 방지

BIA·목표 정의 → RTO/RPO 시간 축 → 세 전략 구조 비교 → 계산·훈련 → failback·오염 복구

- RPO를 서비스 복구에 걸리는 시간이라 쓰지 않습니다.
- Pilot Light를 작은 서비스가 항상 처리 중인 상태로 설명하지 않습니다.

# TA와 AA의 역할·산출물·협업

## 서브노트

### 한눈에 이해

TA는 시스템을 어디에 배포하고 어떻게 운영할지 설계합니다. AA는 업무 기능을 어떻게 나누고 연결할지 설계합니다.

### 정의와 핵심 원리

TA(Technical Architect)는 인프라·플랫폼·연결·배포·비기능 기반의 기술 아키텍처를, AA(Application Architect)는 업무 서비스·모듈·인터페이스·애플리케이션 품질의 구조와 원칙을 책임지는 역할입니다.

- TA는 컴퓨트·네트워크·스토리지·플랫폼·통합·가용성·보안·성능·관측 구조를 다룹니다. 기술 표준, 배포 토폴로지, 자원·용량 산정, 장애복구·운영 설계서, 기술 검증 결과가 주요 산출물입니다.
- AA는 업무 경계·응용 기능·서비스/모듈 책임·API·트랜잭션·데이터 접근·오류 처리·개발 표준을 다룹니다. 응용 구성도, 서비스/인터페이스 명세, 공통 모듈과 개발지침, 품질속성 설계·검증 결과가 주요 산출물입니다.
- 클라우드 전환에서는 TA가 플랫폼을 골라도 AA가 세션·파일 저장·배치·트랜잭션을 기존 방식으로 유지하면 확장·복구가 막힐 수 있습니다. 두 역할은 비기능 요구와 의존성을 함께 확인하고 설계 결정을 ADR에 기록합니다. 이후 성능 시험과 장애 실험으로 기술 기반과 응용 구조를 검증해야 합니다.
- 책임 분장은 조직마다 달라 유일한 국제 표준 직무표처럼 제시하지 않습니다. DA·보안·운영·업무책임자와 RACI를 합의하고 설계심의·공통 백로그·계약시험으로 변경을 조정합니다.

### 구조·비교·판단

| 구분 | 원리·특징 | 적용·판단 |
| --- | --- | --- |
| TA | 플랫폼·자원·배포·운영 기반 | 인프라 구성도·용량·복구 설계 |
| AA | 업무 서비스·모듈·응용 계약 | 응용 구성도·API·개발 표준 |
| 공동 | 비기능 요구와 품질 증거 | ADR·부하/장애 시험·운영 인수 |

### 적용 예제

**강사 창작 적용 예시: 공공 포털과 ERP 클라우드 전환**

강사 생성 학습 예제입니다. 공식 기준답안이 아닙니다.

**조건:** 대국민 조회는 확장되고 ERP 마감 배치는 정해진 시간에 끝나야 합니다.

1. AA가 조회/마감의 서비스 경계와 트랜잭션을 정합니다.
2. TA가 배포·자원 격리·확장·복구 구조를 설계합니다.
3. 양쪽이 DB 연결 한도, 상태 저장, 배치 재시작, API 계약을 공동 시험합니다.

**결과·해석:** 플랫폼 자동확장과 실제 업무 처리 가능성을 함께 확인합니다.

**전제·주의:** 역할명만으로 계약상 최종 책임을 추정하지 말고 조직의 승인권을 확인해야 합니다.

### 답안 골격과 혼동 방지

역할 범위·목표·산출물 비교 → 클라우드 전환의 상호 의존 → 협업 절차와 검증 사례

- TA는 장비 구매 담당자만을 뜻하지 않습니다.
- AA가 화면 설계만 한다고 축소하지 않습니다.

### 내용을 가리고 회상

1. 자동확장이 있어도 응용이 확장되지 않는 원인은 무엇입니까?
2. 두 역할의 공동 산출물을 두 개 제시하십시오.
3. RACI를 언제 합의해야 합니까?

### 적용 기준과 근거

공통가이드의 목표 응용·기술 구조와 아키텍처 원리에 근거한 역할 정리입니다. 특정 기관 표준 직무 정의와의 일치는 확인이 필요합니다.

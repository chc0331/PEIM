# 형상관리·기준선·IaC

## 서브노트

### 한눈에 이해

버전관리는 파일의 이력을 저장하고 형상관리는 어떤 조합을 승인해 배포했는지까지 통제합니다.

### 정의와 핵심 원리

SCM은 소프트웨어 수명주기 산출물의 식별·변경 통제·상태 기록·감사와 릴리즈를 관리해 무결성과 추적성을 유지하는 활동입니다. 기준선은 공식 검토·승인되어 이후 통제된 변경의 출발점이 되는 형상입니다.

- 형상 식별에서 요구·설계·코드·시험·데이터/스키마·환경설정·빌드 스크립트 등 형상항목과 식별자를 정합니다. 형상 통제에서는 변경 요청→영향분석→승인→구현·시험→기준선 갱신을 수행합니다. 상태회계는 요청과 버전·승인·배포 상태를 기록하고 형상감사는 내용과 산출물 일치를 검토합니다.
- 기능 기준선은 합의된 기능·성능 요구, 할당 기준선은 구성요소에 할당된 설계·인터페이스, 제품 기준선은 시험·인수된 구현과 릴리즈 구성을 대표하는 전형적 분류입니다. 이름과 수립 시점은 개발 수명주기·계약에 맞춰 명시합니다.
- Git·SVN은 소스 버전, 변경/이슈 도구는 승인과 추적, 아티팩트 저장소는 빌드 결과·의존성, CI는 재현 빌드·시험, CMDB는 운영 구성 관계를 지원합니다. Git 태그 하나가 문서·배포·환경까지 자동 통제하지는 않습니다.
- IaC는 인프라의 원하는 상태나 구성 절차를 코드로 기술해 검토·버전·자동 적용합니다. Terraform에서는 plan으로 예상 변경을 확인하고 apply로 적용합니다. 상태 파일과 실제 자원이 어긋나거나 비밀이 노출되지 않도록 관리하고 동시 변경을 통제해야 합니다.

### 구조·비교·판단

| 구분 | 원리·특징 | 적용·판단 |
| --- | --- | --- |
| 버전관리 | 파일 변화·브랜치·병합 | 형상관리의 지원 도구 |
| 형상관리 | 승인된 구성·변경·증거 | 요구부터 운영 환경까지 포함 |
| IaC | 인프라 변경의 코드화 | 재현·검토·자동화와 상태 보호 |

### 적용 예제

**강사 창작 적용 예시: 긴급 패치의 기준선**

강사 생성 학습 예제입니다. 공식 기준답안이 아닙니다.

**조건:** v1.2 운영 버전에서 결제 결함이 발견됩니다.

1. 변경 요청과 영향받는 요구·코드·시험을 연결해 승인합니다.
2. 패치 커밋·의존성·컨테이너 digest·IaC 버전을 함께 식별합니다.
3. 시험·감사 뒤 v1.2.1 기준선을 확정하고 실제 배포 구성을 기록합니다.

**결과·해석:** 원인을 재현하고 승인된 버전으로 복귀할 수 있는 구성을 남깁니다.

**전제·주의:** 긴급 변경도 사후 승인·추적·시험 증거를 생략하는 면책 절차가 아닙니다.

### 답안 골격과 혼동 방지

SCM 정의·4활동·절차 → 기준선 종류·변경 통제 → 도구 역할·IaC 적용 예

- baseline은 변경 불가능이 아니라 통제된 변경의 기준입니다.
- Terraform 상태 파일에 민감정보가 있을 수 있습니다.

# 서버리스 컴퓨팅

## 서브노트

### 한눈에 이해

서버가 없어지는 것이 아니라 실행 환경의 준비·확장을 서비스 제공자가 맡고, 사용자는 업무 코드를 중심으로 구성합니다.

### 정의와 핵심 원리

서버리스는 서비스 제공자가 서버의 준비와 운영을 맡고, 요청이나 이벤트에 따라 코드를 실행하고 확장하는 운영 모델입니다. 함수형 서비스(FaaS)와 관리형 백엔드를 조합할 수 있습니다. 이벤트를 받는 장치, 함수, 권한, 상태를 저장할 외부 저장소가 주요 구성 요소입니다.

- 함수는 이벤트를 받아 짧은 작업을 수행하고 응답하거나 다른 서비스에 결과를 저장합니다. 유휴 자원 관리가 줄고 부하에 맞춰 확장할 수 있습니다. 첫 실행 지연, 실행 시간 제한, 외부 서비스 의존과 제공자 종속은 별도로 검토합니다. 요금은 호출 횟수, 실행 시간, 자원, 데이터 전송량 등에 따라 달라집니다.
- 실행 환경은 다시 쓰일 수 있지만 다음 호출에도 상태가 남는다는 보장은 없습니다. 필요한 상태는 외부 저장소에 보관합니다. 이벤트 중복·재시도·순서 역전·부분 실패를 고려해 멱등 키, 중복 제거, 실패 큐, 타임아웃, 추적 ID를 사용합니다.
- 함수가 자동으로 늘어나도 DB 연결 수, 하위 API의 할당량, 계정에서 허용하는 동시 실행 수에는 한도가 있습니다. 큐와 동시 실행 수 설정 등으로 처리 속도를 조절하고 최소 권한, 비밀 관리, 로그 보호를 적용합니다. 작업이 오래 걸리거나 부하가 계속 높다면 다른 방식의 총비용과 비교합니다.
- 관측에는 호출 수뿐 아니라 실패율·재시도 수·동시성·하위서비스 지연·작업당 비용을 함께 사용합니다.

### 구조·비교·판단

| 구분 | 핵심 원리 | 적용·한계 |
| --- | --- | --- |
| FaaS | 이벤트마다 함수 실행 | 첫 실행 지연, 실행 시간 제한 |
| 컨테이너 서비스 | 이미지 단위 실행과 서비스 운영 | 수명과 확장 설정을 조절하기 쉬움 |
| 전통 서버 | 용량과 운영을 직접 관리 | 지속 부하 예측과 운영 책임 |

### 적용 예제

**이미지 업로드 후 썸네일**

강사 생성 학습 예제입니다. 공식 기준답안이 아닙니다.

**조건:** 이미지 파일이 올라오면 썸네일을 만듭니다. 같은 파일의 생성 이벤트가 두 번 전달될 수 있습니다.

1. 객체 버전과 작업 종류로 멱등키를 생성합니다.
2. 같은 키로 들어온 두 호출이 동시에 처리하지 않도록 먼저 처리권을 한 번만 확보합니다. 작업이 끝났다면 기존 결과를 사용합니다.
3. 변환에 실패하면 정해진 횟수만큼 다시 시도합니다. 계속 실패하면 실패 큐로 보냅니다.
4. 처리량을 늘리기 전에 스토리지·DB의 한도를 확인하고 비용 경보를 설정합니다.

**결과·해석:** 같은 이벤트가 다시 도착해도 같은 결과를 쓰고, 동시에 몰린 호출은 처리 한도 안에서 관리합니다.

**전제·주의:** 자동 확장은 제공자의 한도에 따릅니다. 보안 수준과 비용은 실제 구성과 부하를 기준으로 평가합니다.

### 답안 골격과 혼동 방지

정의와 이벤트 흐름 → 구성 요소 → 장단점 → 멱등 처리 예제 → 도입 판단

- 물리 서버의 운영은 서비스 제공자가 담당합니다.
- 보존해야 할 파일은 함수의 로컬 저장소에만 두지 않습니다.

### 내용을 가리고 회상

1. 같은 이벤트가 여러 번 전달될 때 멱등 처리가 필요한 이유는 무엇입니까?
2. 함수가 자동 확장돼도 하위 서비스를 별도로 보호해야 하는 이유는 무엇입니까?
3. 실행 환경이 새로 준비되는 지연(콜드 스타트)은 어떻게 측정합니까?
